# Грабли и интеграционный контракт (oak-server)

Уроки из пойманных багов — не воспроизводить. Формат: **правило** + почему + фикс.

## Auth / Security

- **`/ws` должен быть `permitAll` в `SecurityConfig`.** Рукопожатие WebSocket — HTTP-запрос через Spring Security; JWT при этом ещё нет (он в STOMP-фрейме `CONNECT`, не в заголовках рукопожатия). Аутентификация — на STOMP-уровне в `AuthChannelInterceptor` (читает JWT из заголовка `CONNECT`). «Закрытие» `/ws` = 401 на рукопожатии, WS не поднимется.
- **STOMP native-заголовки чувствительны к регистру** (Spring сопоставляет по точному ключу, а не case-insensitive-спеке). `AuthChannelInterceptor` проверяет и `Authorization`, и `authorization`; клиент шлёт `Authorization` с большой буквы — держать регистр согласованно между клиентом и сервером.
- **Reuse-detection + `@Transactional` rollback.** Family-revoke при переиспользовании refresh-токена делается ДО бросания 401; `ResponseStatusException` пометил бы tx rollback-only и revoke откатился бы. Поэтому `AuthService.refresh` несёт `@Transactional(noRollbackFor = ResponseStatusException.class)`. Не «чинить» убиранием `noRollbackFor`.
- **Чистка refresh-токенов — по `expiresAt`, а не по факту `revoked`.** Отозванный-но-не-истёкший токен нужен для reuse-detection украденной копии. Поэтому `deleteByExpiresAtBefore` (не `deleteByRevokedTrue`).
- **Self-invocation ломает `@Transactional` у `@Scheduled`.** Планировщик входит через CGLIB-прокси, но зовёт `purgeExpired()` на `this` — мимо прокси, транзакция не применяется → `TransactionRequiredException` на каждом прогоне; тест, звавший метод извне, баг не видел. Правило: `@Scheduled`-метод, вызывающий транзакционный метод того же бина, обязан нести `@Transactional` сам. Регресс — `RefreshTokenCleanupTest`.
- **`/api/auth/refresh` логируется построчно (`[auth-refresh]`)** — диагностика «Session expired»: `rotated` / `REUSE` / `rejected` / `BANNED`; поле `fp` (8 символов сырого токена) зеркалится клиентским логом — коррелировать два лога по `fp` при разборе инцидентов; `from` отличает машины.
- **RBAC — banned НЕЛЬЗЯ выразить через `UserDetails.enabled`/`accountNonLocked`.** `DaoAuthenticationProvider` кидает `DisabledException`/`LockedException`, а `login` ловит только `BadCredentialsException` → забаненный получал бы 500 вместо 403. `PrincipalUser` несёт `banned` отдельным полем, статусы Spring всегда `true`; login читает banned прямо из JPA-сущности. НЕ «оптимизировать» в `.disabled(user.isBanned())`.
- **RBAC — ban enforced немедленно:** `JwtAuthenticationFilter` (после `loadUserByUsername` → `PrincipalUser.isBanned()` → `sendError(401,"banned")` + `return` без `doFilter`; пиггибэк на существующий lookup, 0 доп. запросов), `AuthService.login` → 403, `AuthService.refresh` → отзыв всей семьи + 401, `AuthChannelInterceptor` — STOMP CONNECT. Access-JWT живёт 8 ч — бан не должен ждать перевыпуска. Кик — кооперативный (`/user/queue/member.kick`, клиент сам отключается); бан — единственное, что предотвращает re-entry.

## RBAC

- **Bitmask `Permission` по `ordinal()` стабилен: НЕ переупорядочивать константы.** Бит = `1L << ordinal()`, persisted как `long` на `Role`/`ChannelRoleOverride`; перестановка молча перемапит все сохранённые маски. Новые права — только дописывать в конец группы. Клиенту отдаём `Set<String>` имён, не сырую маску.
- **`@everyone` НЕ в `user_roles`** — built-in (`kind=EVERYONE`), сеется `RoleSeeder`, всегда подмешивается в резолв (`effectiveBase`/`hasInChannel`). Дефолты держат приложение юзабельным (send/read/attach/connect/speak). VIEW_CHANNEL обязан быть последним элементом enum; существующие БД без нового бита закрываются безусловным ре-грантом `ensureEveryoneViewChannel()` при каждом старте (инфраструктура, не ручная SQL-заметка).
- **OWNER — это роль, не флаг** (`kind=OWNER`, `position=MAX_VALUE/2`, `ADMINISTRATOR`, protected). Бутстрап: первый зарегистрированный → OWNER; fallback для dev-БД — сидер промоутит мин-id юзера. OWNER-цель иммунна; OWNER нельзя назначить через `assignRoles` (только transfer).
- **Principal-асимметрия:** REST principal=`UserDetails` (`getUsername()`), STOMP principal=username-строка (`Principal.getName()`). `AuthorizationService` принимает `String username` в обоих путях. Чеки — явные (`requireServer`/`requireInChannel`/`requireCanActOn`, кидают 403), НЕ `@PreAuthorize` (method-security выключен; права резолвятся из БД — смена роли生效 без перевыпуска JWT).
- **Новая NOT NULL-колонка на уже населённой таблице требует `default` в `columnDefinition`** (`boolean default false`), иначе Postgres отвергает alter, Hibernate WARN, колонки нет — и первый селект падает. Общее правило для `ddl-auto=update`.
- **Удаление роли:** `user_roles` и `channel_role_overrides` без CASCADE — чистить assignments ДО `roleRepository.delete` (+ flush, чтобы override-DELETE ушёл раньше). НЕ bulk-`@Query delete` — оставляет stale-сущности в persistence-context (`TransientPropertyValueException` в следующем flush); загружать и `deleteAll`.
- **Слоистая резолюция оверрайдов, не аккумуляция:** слои (everyone → roles → member) применяются последовательно `(mask | allow) & ~deny` — иначе member-allow не перебьёт everyone-deny. Регресс-тест `roleAllowBeatsEveryoneDeny`.
- **VIEW-мастер-гейт в `hasInChannel`** — одно место покрывает все channel-permission call-site. SUBSCRIBE-гейт TEXT/VOICE — по READ, не по VIEW (locked-канал виден, подписка на тему легальна; гейт subscribe-time-only — живая подписка переживает флип прав; интерсептор — `ChannelSubscriptionInterceptor`).

## WebSocket / messaging

- **`SessionDisconnectEvent` может прийти >1 раза за сессию** — компоненты идемпотентны по `sessionId` (`remove` возвращает null на дубле → no-op); граничные решения 0↔1 сериализованы одним локом (исключает гонку порядка online/offline). Principal: `StompHeaderAccessor.wrap(event.getMessage()).getUser().getName()`.
- **`setHeartbeatValue` требует `TaskScheduler`** — иначе `IllegalArgumentException` при старте брокера. В `WebSocketConfig` планировщик создаётся inline (`ThreadPoolTaskScheduler`, daemon, `initialize()`).
- **`@MessageMapping` сканируется только на `@Controller`-бинах** (`SimpAnnotationMethodMessageHandler.isHandler`); `@Component`/`@Service` → «No matching message handler methods».
- **STOMP-обработчики крутятся БЕЗ `OpenEntityManagerInView` → `LazyInitializationException`** на ленивых коллекциях (OEiV открывает сессию только на HTTP). `AuthorizationService.findUser` грузит роли eagerly (`left join fetch`); любой будущий STOMP-обработчик с БД — либо eager-fetch, либо `@Transactional` на методе.
- **НОВЫЙ per-channel-топик = парная правка regex в `ChannelSubscriptionInterceptor` (иначе DM-утечка).** Простой брокер НЕ авторизует `SUBSCRIBE`; приватность DM-тем держится только на интерсепторе (`^/topic/channel\.(\d+)(?:\.edited|\.deleted|\.reactions)?$`). Любой будущий суффикс `/topic/channel.{id}.*` обязан попасть в regex. **MockMvc это НЕ ловит** (нет WS-слоя) — только ручной smoke.
- **WS-рукопожатие и cross-client доставка не покрываются MockMvc.** DEBUG у `org.springframework.web.socket`/`messaging.simp` — только для отладки: по умолчанию INFO, иначе пинг-кадры (10 с) замусоривают суточное retention-окно лога.

## JPA / схема

- **`ddl-auto: update` НЕ удаляет колонки** (только добавляет таблицы/колонки). Убрать колонку из модели ≠ убрать из БД — либо ручной ALTER, либо миграция. Схемой владеет Flyway (validate на живом старте — страховщик дрейфа).
- **`ddl-auto: update` НЕ обновляет enum CHECK-constraint.** Для `@Enumerated(STRING)` при генерации схемы создаётся check со значениями enum на тот момент; новые значения enum не пересоздают check → insert падает на живом Postgres. H2 (`create-drop`) не ловит — только smoke. Фикс: ручной DROP+ADD CONSTRAINT. Правило: новое значение string-enum на населённой таблице = ручное обновление check.
- **Мёртвая `NOT NULL`-колонка блокирует INSERT'ы, маскируясь под 409.** Прецедент: забытая `users.email` (NOT NULL) — Hibernate не вставляет email → `DataIntegrityViolationException` → catch выдавал «Username already exists», вводя в заблуждение. Симптом: регистрация любого имени → 409, логин существующих работает.
- **Singleton-сущность (`ServerProfile`) — адресовать `findFirstByOrderByIdAsc`, НЕ хардкод `findById(1L)`:** IDENTITY делегирует id sequence, `setId(1L)` всё равно INSERT, и строка может получить id≠1. Сидер идемпотентен через тот же `findFirstByOrderByIdAsc`.
- **`@MessageMapping` + derived-имя репозитория:** суффиксы после свойства (`findByChannelIdWithUser`) Spring парсит как свойство → `PropertyReferenceException` на старте контекста. Правильно `findWithUserByChannelId` (`find<Произвольно>By<Свойство>`).

## REST / сервисы

- **`Page.getContent()` неизменяем** — `Collections.reverse(...)` → `UnsupportedOperationException` при ≥2 элементах (при 1 — no-op, тест с одним элементом баг пропускает). Копировать `new ArrayList<>(...)`. «Последние N по возрастанию» = `DESC + LIMIT` + reverse.
- **Presigned-URL печатаются на `publicEndpoint`**, не на внутреннем `endpoint` — иначе клиент не дойдёт до MinIO. SDK: `GetPresignedObjectUrlArgs.getPresignedObjectUrl` (класса `GetPresignedUrlArgs` нет). В test-профиле MinIO выключен, `NoopAttachmentUrlSigner` подменяет подписчика.
- **Аватар: сервер байты не терминирует → MIME-проверка только по расширению** (png/jpg/jpeg, иначе 400), размер — на клиенте. Не добавлять multipart-приём/MIME-sniff — ломает принцип «presigned-URL, без BLOB в PostgreSQL». Upload двухшаговый (slot → PUT → `/confirm`) — упавший upload не оставляет dangling key; замена/снятие удаляет старый объект, orphan'ы не копятся.
- **`Message.editedAt` — ручная установка, НЕ `@UpdateTimestamp`** (штампует каждый UPDATE и рассчитан на непустое; `editedAt` nullable и ставится ровно в `MessageService.edit`). Сравни `createdAt`: `@CreationTimestamp` + `updatable=false`.
- **`record MessageResponse` — wire-совместимость:** новые поля ТОЛЬКО в конец и синхронно с клиентским зеркалом (клиент НЕ отключает `FAIL_ON_UNKNOWN_PROPERTIES` — старый клиент против нового сервера упадёт). Согласованная ЗАМЕНА полей законна только при парном dev-деплое (прецедент: скалярные аттачи → список) = одновременная правка обоих зеркал + literal-JSON тестов + миграция колонок.
- **`toResponse` не ходит в репозиторий** (N+1-инвариант): реакции/цитаты передаются ПАРАМЕТРОМ, батчи делает вызывающий (`findByMessageIdIn` на страницу). Пустой guard (`ids.isEmpty() → Map.of()`) держит strict-Mockito-тесты.
- **Правило reply-пинга синхронизировано в ДВУХ местах** — `MessageService.withReplyMention` и `ReadStateService.countMentionsOf`: менять только вместе, иначе бейджи разъедутся с mentions.
- **MockMvc: `jsonPath("$.x").exists()` считает ЯВНЫЙ null отсутствующим** — noop-сигнер даёт `{"url":null}`; проверять через `JsonPath.read(...)` + `assertNull`.
- **void-методы Mockito не стабятся `when()`** («'void' type not allowed here») — только `doThrow(...).when(mock).method(...)`.
- **Упоминания парсятся на read-time, БЕЗ БД-колонки** (`toResponse` — единая точка). Mentions не персистятся → rename оставляет старые `@` простым текстом (задокументированный tradeoff). `@everyone`/`@here` резолвятся по ЛИТЕРАЛУ через `findByKind(EVERYONE)`; non-mentionable роль не consumes токен. Имя роли валидируется `[A-Za-z0-9_-]{1,32}` (пробел ломает plain-`@token` grammar).
- **Read-state:** `lastReadMessageId==null` → readFloor=0 («never read» = считать все); bootstrap `seedInitialReadStates` ставит новичку lastRead=current-latest (архив не unread). `ack` МОНОТОННЫЙ (новое lastRead < текущего → no-op) — ack из частичного окна не откатывает указатель. mentionCount — аппроксимация по freshest-200.

## Инфраструктура / dev-машина

- **`TURN_EXTERNAL_IP` в `env/.env` = LAN-IP машины** (не `127.0.0.1`, не публичный) — coturn рекламирует relay-кандидаты с ним. Карта TURN-на-Docker-Desktop/Windows: (1) libwebrtc молча выбрасывает loopback-адрес TURN (`turn:localhost` → НОЛЬ relay-кандидатов, ICE вечно CHECKING); (2) через UDP port-proxy coturn видит клиента как gateway `172.x.0.1` → TURN-permission режет весь peer-трафик (`rp=0/sp=0`); (3) `network_mode: host` не экспонирует порты на Windows-хост. **Итог: полноценный RELAY-смоук на этой dev-машине невозможен** — только реальный Linux или две машины через достижимый TURN.
- **Старт устойчив к неготовой периферии** (ждать Postgres, а не падать) — поймано на dev: зависит от порядка поднятия compose.

## JPA / Spring Data (уроки 2026-11-24, инцидент молчаливых иконок)

- **`@Modifying`-запросу нужна своя `@Transactional`**, если его зовут НЕ из запроса: контроллерные пути получают транзакцию контекста, а фоновый поток (executor лейна иконок) — НЕТ → `TransactionRequiredException`. Баг прожил релиз невидимым, потому что сложились три дыры: (1) юнит-тесты звали репозиторий моком (мок не знает про транзакции), (2) интеграционный класс `@Transactional` — его транзакция ДАРИТ стору то, чего в проде нет (тест-поток = поток транзакции), (3) `ThreadPoolExecutor` проглатывает uncaught-исключения FutureTask молча. Правила: кастомный `@Modifying` на интерфейсе репозитория — всегда с `@Transactional` (CRUD-методы SimpleJpaRepository имеют свою, кастомные — НЕТ); фоновые задачи — try/catch(Throwable) с громким log.error; **тест фонового пути обязан гонять настоящий репозиторий с закоммиченными фиксстурами** (см. `SgdbIconLaneIntegrationTest` — класс без `@Transactional` с самоочисткой: `refreshTokens.deleteAll()` → `users.deleteAll()`, иначе FK из refresh_tokens роняет очистку).
- **Тестовая транзакция скрывает отсутствие продовой**: `@Transactional`-тест любого HTTP-пути_green при красном проде для того же кода с фонового потока. Симптом-маркер: «работает в тесте, тихо умирает в фоне».
